# Koven desktop

Tauri 2 shell wrapping the Koven web client (`client/dist/`) into a native
window for macOS, Windows, and Linux.  Talks to the live homeserver at
`https://client.koven.chat` for all Matrix + engine API calls; external links
in chat (YouTube, docs, anything off-domain) are dispatched to the user's real
browser via the `tauri-plugin-opener` plugin.

The shell is intentionally thin.  Anything that can live in the web client
lives there.  This binary adds only what *requires* native context: window
chrome, OS link dispatch, native notifications, single-instance focus, and a
signed in-app updater.

## Layout

```
apps/desktop/
  package.json           # bun scripts (dev, build, icon)
  src-tauri/
    Cargo.toml           # rust deps (tauri 2, plugins, log, url)
    tauri.conf.json      # window/bundle/updater config
    capabilities/
      default.json       # plugin permissions for the main window
    src/
      main.rs            # entry point — calls lib::run()
      lib.rs             # plugin wiring + nav guard + updater
    icons/               # generated by `bun run icon /path/to/png`
```

## Develop locally

```sh
bun run desktop:dev      # from the repo root
# or:
bun install --cwd apps/desktop
bun run --cwd apps/desktop dev
```

In dev mode the WebView loads the live SPA at `https://client.koven.chat`
directly — no Vite dev server needed for the shell-side workflow.  If you
want to hot-reload against a checked-out client/, edit the `WebviewUrl`
in `src/lib.rs`'s `setup` block to point at `http://localhost:5173`.

## Production build

```sh
bun run desktop:build
```

Outputs go to `apps/desktop/src-tauri/target/release/bundle/`:

- macOS → `macos/Koven.app` (the bundle directory) plus the
  `Koven.app.tar.gz` updater artifact in `bundle/macos/`.  The
  `.tar.gz` is the user-facing download — Sparkle-style zip flow,
  no `.dmg`.
- Windows → `nsis/Koven_<version>_x64-setup.exe`
- Linux → `appimage/Koven_<version>_amd64.AppImage`, `deb/koven-desktop_<version>_amd64.deb`

The build pipeline:

1. `bun install` (root + apps/desktop)
2. `bun run --cwd ../../../client build` (compiles the SPA into `client/dist/`)
3. `cargo tauri build` (compiles the Rust shell, embeds `client/dist/` as
   bundled resources, signs the updater artifact with the minisign key from
   the `TAURI_SIGNING_PRIVATE_KEY` env var, packages per-platform installers)

## External link handling

Every top-level navigation request flows through `is_internal()` in
`src/lib.rs`.  Allowed origins:

| Origin | Why |
| --- | --- |
| `tauri://localhost` | Bundled SPA on macOS / Linux |
| `https://tauri.localhost` | Bundled SPA on Windows (WebView2 quirk) |
| `https://client.koven.chat` | The live homeserver, served as the dev URL and used for any in-SPA hard navigation |

Anything else gets cancelled and dispatched to the user's default browser via
`OpenerExt::open_url`.  This covers `<a target="_blank">` clicks,
`window.open(...)` calls, and JS-driven `location = ...` redirects equally —
they all surface through `WebviewWindow::on_navigation`.

## Code signing

### macOS — Developer ID + notarization

In CI the workflow reads the cert + Apple ID from these GitHub secrets:

| Secret | Source |
| --- | --- |
| `APPLE_CERTIFICATE` | base64 of the `.p12` exported from Keychain Access |
| `APPLE_CERTIFICATE_PASSWORD` | the password you set when exporting |
| `APPLE_SIGNING_IDENTITY` | full identity string, e.g. `Developer ID Application: Christopher Hill (XXXXXXXXXX)` |
| `APPLE_ID` | Apple ID email used for notarization |
| `APPLE_PASSWORD` | app-specific password from appleid.apple.com |
| `APPLE_TEAM_ID` | 10-char team ID |

Local builds use whichever Developer ID Application cert is in the keychain.

### Windows — Authenticode (not yet wired)

The `.exe` is currently unsigned.  First launch on a fresh machine triggers
SmartScreen ("Windows protected your PC").  Users dismiss via *More info →
Run anyway*; Windows remembers the choice per-binary.  To remove the warning,
buy an OV/EV cert and add `WINDOWS_CERTIFICATE` + `WINDOWS_CERTIFICATE_PASSWORD`
GH secrets plus a `bundle.windows.signCommand` to `tauri.conf.json`.

### Tauri updater (all platforms)

Separate from OS code signing.  Tauri uses minisign to verify each downloaded
update came from us.  The keypair lives at:

- public key: committed in `tauri.conf.json` under `plugins.updater.pubkey`
- private key: `~/.config/koven-release/desktop.key` on the dev machine, plus
  `TAURI_SIGNING_PRIVATE_KEY` GH secret on `GnosysLabs/koven-chat`

**Don't lose the private key.** Every installed Koven Desktop polls the
updater manifest URL with the embedded pubkey baked into the binary forever.
If the key is lost, every existing user has to manually re-download a new
build signed with a fresh key.

## Releasing

Push a `desktop-v<version>` tag from the repo root:

```sh
# Bump version in BOTH src-tauri/Cargo.toml AND src-tauri/tauri.conf.json,
# they MUST match — tauri-action reads tauri.conf.json's version, but the
# Cargo build picks up Cargo.toml's.

git commit -am "Bump desktop to <version>"
git push
git tag desktop-v<version>
git push origin desktop-v<version>
```

`.github/workflows/desktop-release.yml` picks it up:

1. Matrix builds on macos-latest (×2 archs), ubuntu-22.04, windows-latest
2. Each runner: bun install → `bun run --cwd client build` → `tauri-action`
3. `tauri-action` builds the bundle, signs the updater artifact with
   minisign, uploads the `.dmg` / `.exe` / `.AppImage` / `.deb` plus its
   `.sig` and the constructed `latest.json` manifest as release assets to a
   draft GitHub Release named after the tag
4. `publish` job promotes the draft to public once every platform is up

Released builds become available at:
- The downloadable binaries: `https://github.com/GnosysLabs/koven-chat/releases/tag/desktop-v<version>`
- The updater manifest: `https://github.com/GnosysLabs/koven-chat/releases/latest/download/desktop-latest.json`

Existing installs poll `desktop-latest.json` on launch, verify the signature
against their embedded pubkey, download the platform-specific artifact,
install, and restart on next launch.

## Single-instance & deep-linking

The `tauri-plugin-single-instance` plugin keeps one window per machine — a
second `koven-desktop` launch focuses the existing window instead of spawning
a duplicate.  Future deep-linking (`koven://room/!abc:server` opening to that
room) hooks into the same plugin's argv handler.
